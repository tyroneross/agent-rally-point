# Worktree closeout: independent review and implementation brief

Date: 2026-09-27. Status: review before implementation. Owners: separate Build Loop runs in Agent Rally Point and Easy Terminal. Target: each repository's local `main`, after its current main owner releases it. This document is an implementation contract, not evidence that the changes have shipped.

## Decision

Keep the existing repo-local worktree layout. Add a read-only, Git-grounded closeout view that joins exact agent ownership evidence. Make Rally's implicit session cleanup retain clean worktrees with unmerged commits, and make `worktree gc --apply` honor its documented live-owner rule. Display the same evidence in Easy Terminal's existing Worktrees inspector. Do not create a new mutable worktree registry or infer ownership from a branch name, shared tool label, or pane occupant.

## Evidence and why this scope

- Rally's `worktree plan` uses Git but explicitly cannot attest live ownership (`docs/COMMAND-SEMANTICS.md:140-160`; `crates/rally-cli/src/worktree_plan.rs`). Managed sessions already record exact tool, session, branch, and path (`crates/rally-cli/src/backends.rs:134-187`).
- `rally stop` currently calls worktree cleanup and discards the outcome (`crates/rally-cli/src/lib.rs:11533-11543`). Cleanup can remove a clean worktree whose commits are not merged after preserving a branch/bundle (`crates/rally-cli/src/run_worktree.rs:167-179,241-350`). This is a policy risk, not a confirmed local incident.
- `worktree gc` says a live owner must never be reaped (`crates/rally-cli/src/worktree_gc.rs:16-22`), but the current skip condition requires both a live owner and an unmerged branch (`:225-247`). Its apply report does not check `outcome.worktree_removed` before calling a tree reaped (`:309`). These are concrete implementation defects.
- Easy Terminal already has a Git worktree inspector (`Sources/Workbench/RepoBranchesSection.swift`) and cleanup engine (`tools/et_worktrees.py`). The engine's `owner` is a pane/process occupant, not accountable task ownership (`tools/et_worktrees.py:572-579`). Its Rally UI parser keeps only the first file claim scope (`Sources/Coordination/RallyCoordinationSource.swift:547-559`). Worktree Spaces may lack the main checkout's ignored `.rally` ledger (`Sources/Workbench/OperationsRowCopy.swift:197-205`). The existing Build Loop run ledger is `.build-loop/state.json` with `runs[].createdRefs[]`.
- A historical Build Loop/Rally RCA counted 84 claims tied to dead worktree paths in July 2026 (`build-loop/docs/plans/2026-07-02-C-rally-lifecycle-RCA.md:37-42`). The current Build Loop collapse path releases exact claims, so this is motivation for visible provenance, not a claim that the old failure persists.

## Rally implementation

1. Add `rally worktree closeout --json` as a read-only projection with its own versioned schema; leave `worktree plan` v1 unchanged. Start from Git worktree rows and join active managed sessions by canonical exact path plus repo identity and exact session ID. Check branch/HEAD for inconsistency; never use them alone as ownership proof. Join claims only by exact `(tool, from_session_id)` for those sessions. Record the intended merge target commit/ref when provisioning new managed sessions and compare mergedness against that stable target; legacy sessions without a provable target yield unknown rather than a comparison against moving canonical HEAD. Label each source and its freshness. A missing, stale, conflicting, or unprobeable source yields `unknown`, not `unowned` or `ready`. The output must distinguish `merged`, `unmerged`, `dirty`, `detached`, `missing`, `live_owner`, `no_live_owner_observed`, and `unknown` as facts/statuses; its closeout recommendation remains advisory.
2. Session lifecycle: `stop`, managed task completion, and `sessions --reap` all reach shared worktree cleanup (`lib.rs:8624-8649,9250-9270,11533-11543`). Enforce the retention rule in shared `run_worktree::cleanup` or prove every call site follows an equivalent rule. Stop the process and release its session authority independently of source cleanup. `stop` must confirm backend process death before removing even a merged worktree; a failed or uncertain stop retains it and reports the disposition (`lib.rs:11517-11543`). Task completion may use confirmed exit; reaping needs a fresh stale/dead probe. Retain any worktree with unmerged commits, even when clean. Return a visible disposition containing path, branch, merged/dirty state, whether a bundle was written, whether removal happened, and reason; update completion text so it does not say only dirty trees are retained. Explicit worktree cleanup remains a separate action after ownership and Git checks. Do not silently turn task completion into deletion of unmerged source.
3. `worktree gc --apply`: derive ownership from exact managed session path and ID, not the current branch-prefix/presence heuristic (`worktree_gc.rs:30-38`). Never remove a worktree whose exact managed owner is live, whether merged or not. If ownership evidence is unavailable or conflicting, retain the tree. Probe liveness before any removal. Mark `reaped` only when removal actually succeeded. Surface retained/failed reasons distinctly. Keep the existing no-force safety policy for dirty worktrees and ambiguous ownership.
4. Cover exact session joins, two sessions sharing one tool ID, detached/missing trees, unavailable ledger, clean unmerged commits, merged live owner, failed cleanup outcome, and read-only/no-write behavior. Keep bounded command runtime comparable to the planner's existing watchdog.

## Easy Terminal implementation

1. Add a read-only closeout/ownership row to the existing `RepoBranchesSection` worktree inspector. Reuse existing Git triage. Resolve the repository by Git common directory/main checkout, then match worktree by canonical path. Show branch/HEAD consistency, Rally exact session/claim evidence from the new typed closeout projection, and Build Loop state from both `state.execution.run_worktree_path` (an active Phase 1 tree may exist before a `runs[]` entry) and `runs[].createdRefs[]`. Match run ID, path, branch, lifecycle status, and freshness when those fields are available; missing identity cannot assert ownership absence. Closed historical refs are history, not active ownership; open, kept-for-review, surfaced-unmerged, and error states need distinct display/decisions. Build Loop metadata is evidence of a run, not authority to remove a tree. Show provenance and `current`, `stale`, `unavailable`, or `ambiguous` availability.
2. Keep ET functional when Rally CLI or Build Loop state is absent. An absent source is `unavailable`; an empty verified source is `no active owner observed`; contradictory matches are `ambiguous`. Do not label a tree `ready` based only on an empty owner field. Do not repurpose the cleanup engine's pane/process `owner` as an accountable agent identity.
3. Preserve one cleanup engine, but gate its existing Remove action at the engine boundary and the UI. A Git-clean/merged verdict alone cannot authorize removal: for a repo participating in Rally or Build Loop, require fresh, exact repo/path evidence, no live or ambiguous Rally owner, and no open matching Build Loop run ref; retain the existing pane/process and Git guards. Detect participation from the canonical checkout's actual `.rally` and `.build-loop/state.json` sources, not a worktree-local absence. If a participating source is unavailable, stale, or ambiguous, show why cleanup is blocked. A repo with neither system present may retain Git-only cleanup with an explicit unmanaged-repo label and the existing live pane/process guards; that label makes no claim about agent ownership. ET's read-only browsing remains functional without Rally CLI. Recheck at click/removal time to avoid a stale preview. Do not add a second cleanup engine or registry. Any override that bypasses unknown ownership is outside this first change.
4. Run `et design brief --paths <changed files>` before UI/behavior edits. Follow `docs/design/decisions.jsonl`, especially the exact native-Rally/ledger-compatible decision. Verify real temp Git worktree tests, Swift model/decoding tests, `bash build.sh` with `BUILD SUCCEEDED`, and native accessibility inspection of narrow, empty, unavailable, and ambiguous inspector states. Do not use mock data in shipped UI.

## Merge baseline and research comparison

This is descriptive context, not an acceptance target. As of local `main` heads Rally `dec188e`, Build Loop `70d4888`, and Easy Terminal `4d14a07`, a read-only replay of each first-parent two-parent merge's parents via `git merge-tree --write-tree --messages P1 P2` found `CONFLICT (content)` in Rally 9/51 (17.6%), Build Loop 21/119 (17.6%), and Easy Terminal 23/98 replayable (23.5%). Combined: 53/268 (19.8%). Three Easy Terminal unrelated-history import merges could not be classified. Among conflict merges, distinct conflicting-file median/p90/max were Rally 2/3/3, Build Loop 3/7/18, Easy Terminal 1/2/4. Build Loop's largest cases include mirrored `plugin-artifacts/codex` copies. Branch-side median churn (merge base to second parent, added plus deleted text lines) was Rally 925, Build Loop 847, Easy Terminal 668; 208/268 sides exceeded 185 lines. These are not original PR diffs or observed failed attempts. The replay omits aborted attempts, rebase/cherry-pick conflicts, resolution time, and semantic conflicts; intentional null merges can replay as textual conflicts.

Size-stratified local replay: branches with at most 185 lines of churn conflicted 9/60 (15.0%); larger branches conflicted 44/208 (21.2%). Two Build Loop commits explicitly labeled null merges replay as content conflicts; excluding only those gives 51/266 (19.2%), with size strata 8/59 (13.6%) and 43/207 (20.8%). This sensitivity check changes the aggregate little. Excluding mirrored `plugin-artifacts/codex/` lines from Build Loop churn does not move any branch across the 185-line threshold. The strata are small, especially per repo, and do not control for task type, overlap, era, or tool exposure.

The [AgenticFlict paper](https://arxiv.org/html/2604.03551v2) selected open or closed-unmerged agent PRs, simulated `git merge --no-commit --no-ff` against a base/head snapshot, identified unresolved files with `git diff --name-only --diff-filter=U`, and counted textual conflict-marker regions. It reports 29,609 conflicted among 107,026 successfully simulated PRs (27.67%); 35,626 candidates were excluded. Its Table 1's 75,924 clean PRs plus 29,609 conflicting PRs sum to 105,533, leaving 1,493 of the reported simulated denominator unexplained, so the published categories do not fully reconcile. A conflicting PR had median 2 files and mean 4.36 files, 11.36 regions, and 540.42 conflict-marker lines. Its churn analysis defines size as added plus deleted lines and reports roughly 9.9% conflict for a 2-line median-churn bin, nearly 30% at 25 lines, and roughly 32–33% around 46–185 lines, remaining high for larger changes. Its selection and denominator differ materially from our completed merge commits. The numerical 7.9-point gap between 27.67% and 19.8% is not a performance effect attributable to Rally, Build Loop, or Easy Terminal.

The [CAID study](https://arxiv.org/html/2603.21489v2) compared isolated worktrees to agents sharing a workspace under instruction-level separation. Reported task scores were 63.3 versus 55.5 on PaperBench and 59.1 versus 56.1 on Commit0-Lite. Those are task-quality results for one system, not measured conflict-rate improvements in these repositories. The plausible benefit here is fewer simultaneous checkout collisions and better ownership/cleanup decisions. A causal local benefit would require prospective records of all attempted integrations, overlap/size, actual conflicts and resolution effort, and tool exposure; do not infer it from the historical rates alone.

The Rally implementation produces its typed projection and lifecycle fix first; ET consumes that schema or a compatible fixture while preserving absent-CLI behavior.
